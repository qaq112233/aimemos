# Memogram AI 个人笔记机器人需求

更新日期：2026-10-25。用途：交接给新对话实施 MVP。本次交付仅包含文档。

## 1. 目标与实施原则

通过 Telegram 收集资料，使用 AI 生成和反复修改 Markdown 草稿，确认后保存到自建 Memos；同时保留完全不经过 AI 的原样保存方式。

- 使用 Go，Docker Compose 部署到个人 Linux 服务器，优先轻量、简单、低维护成本。
- 基于 [Memogram](https://github.com/usememos/telegram-integration) 的当前代码改造，优先复用 Memos 客户端、Telegram 附件处理及已有测试。开发前重新检查上游版本和结构，不凭旧代码印象直接修改。
- 首版只实现单用户 Telegram 私聊、一个活动素材组。对接用户实际部署的最新 Memos，联调时记录确切版本。
- 素材、草稿和对话保存在内存，重启允许丢失；无需为这些内容引入 SQLite 或其他数据库。
- 允许采用成熟 Go 库。只写必要的业务代码和少量适配，不自行开发通用 AI SDK、Bot 框架或插件系统。
- 后续可能接入 QQ、钉钉等 Bot，以及向量／语义搜索；首版保持职责分离，不实现这些远期功能。

## 2. 素材收集与交互

1. 用户连续发送或转发文字、链接、图片、相册，默认加入当前素材组；第一条素材自动开始收集。
2. 消息可能间隔几秒或更久。等待时间只用于减少状态提示，不用于自动分组、生成或保存。
3. Bot 简洁显示已收集的素材数量和类型，避免每条消息都回复一长段菜单。
4. 用户通过可配置的数字指令或按钮，明确选择处理方式。
5. AI 整理后展示草稿，支持自然语言多轮修改，也支持中途补充素材。
6. AI 草稿只有在点击“确认保存”后才写入 Memos。原样保存指令本身就是明确的保存操作。
7. 保存成功返回 Memos 链接，结束本组；放弃则清空本组。

数字与行为的对应关系尚未最终确定，必须集中配置，容易修改。以下只是首版候选映射：

| 示例入口 | 处理方式 | AI 图片输入 | 保存时机 |
| --- | --- | --- | --- |
| `1` | 按接收顺序合并原始文字、链接与附件 | 不调用 AI | 直接保存 |
| `2` | 简单整理文字 | 关闭，图片仍作为附件保存 | 草稿确认后 |
| `3` | 深度整理为教程 | 开启 | 草稿确认后 |
| `4 提示词` | 使用本次自定义要求整理 | 默认开启，可由整理方案调整 | 草稿确认后 |

收集状态中，只有用户本人发送、完整匹配入口规则的消息才作为指令；转发内容或图片说明中的数字按素材处理。不要依赖 AI 判断每条消息是素材还是指令。

草稿状态中，普通文字默认是修改要求；转发和图片默认补充为素材。通过“补充素材”按钮进入收集状态，可补充自己输入的文字，再重新选择整理方式。已有草稿保留，无需每轮重新输入全部要求。

每次生成使用明确的素材快照。生成期间仍能接收素材，但新素材不悄悄混入本次结果；显示“新增素材尚未纳入”。不要把不含新增素材的草稿显示成已经完整更新。

“确认保存”始终保存对应的草稿版本。旧按钮和重复点击不能在同一运行会话里反复创建笔记。

## 3. 内容与草稿要求

- 文字、转发来源信息、图片说明和附件归属应保留；原样保存不改写文字，按消息顺序合并。
- 链接仅保留网址和附带文字。首版不抓网页正文，不假装已阅读链接内容。
- 简单整理只优化文字结构、段落、标点和表达，默认保留信息，不把它自动变成短摘要；不把图片送给 AI。
- 教程整理可结合图片内容，组织前提、步骤、命令和注意事项；缺失的关键步骤应标明待确认，不编造环境、命令执行结果或成功结论。
- 自定义整理使用本次提示词，同时遵守来源、标签和保存规则。
- 图片理解只在选用支持图片的模型时启用；模型不支持时明确提示用户换模型或关闭读图，不静默丢弃图片输入。
- 草稿保存标准 Markdown；Telegram 展示可用阅读预览或分段，不把任意 AI Markdown 直接当 Telegram 格式发送。
- 最终笔记保存整理后的正文、标签、相关来源链接及附件，不在末尾重复附上整份原始文字。
- 首版图片默认作为 Memos 附件保存，不要求实现复杂的正文内插图排版。
- 图片中的重要信息如果参与了笔记结论，应自然写入正文或简短图注，方便日后按文字检索。
- 草稿继续修改时保留有效的先前要求，不因切换模型或新增素材而随意恢复用户已经删除的内容。

## 4. 多供应商与模型参数

支持多组 OpenAI 兼容服务，包括用户现有的 CLIProxyAPI。实现 Responses 和 Chat Completions 两种协议，供应商与协议不是同一个概念。

| 配置层 | 最少需要的内容 |
| --- | --- |
| 供应商 | 名称、Base URL、Key 的环境变量引用、超时、可选请求头 |
| 模型 | 所属供应商、实际模型名或中转别名、协议、是否支持图片、默认参数 |
| 整理方案 | 名称、提示词、默认模型、参数覆盖、图片开关、标签开关 |
| 入口映射 | 数字或按钮关联哪个整理方案；原样保存作为独立操作 |

用户可能使用 6.1sol、6luna、DeepSeek 等，程序不硬编码这些模型名或可用性，以实际服务提供的模型 ID 和能力为准。

需要支持的可选参数：输出 Token 上限、思考等级、适用时的思考预算、temperature、top_p、输出详细程度，以及结构化的扩展参数。

规则如下：

- 整理方案覆盖模型默认值；如果提供了本次临时设置，再以临时设置优先。首版不必为每个参数开发 Telegram 菜单。
- 未设置的可选参数不发送。思考等级、预算、采样参数不能假定所有模型都支持。
- 适配协议差异，例如 Responses 的 `max_output_tokens`、`reasoning.effort`，以及 Chat Completions 的相应字段；部分兼容服务需要 `max_tokens`，应按模型配置适配。
- 输出上限可能包含思考 Token，不能把它直接等同于可见正文长度。输出因上限中断时应提示，不当作完整草稿。
- 扩展参数与普通参数的覆盖规则明确；整理方案不应直接构造平台消息、认证信息或 AI 输入内容。
- CLIProxyAPI 的模型名思考后缀可能覆盖请求体设置，配置中避免重复定义互相冲突的思考等级。
- 协议明确选择。不要在失败后自动切换供应商、模型或协议反复请求。
- 应用自己维护当前素材、草稿和修改要求，能够在会话中切换已配置模型，不依赖某个供应商独有的会话存储。
- AI 只生成草稿，不能直接执行 Memos 写入或其他工具操作。

固定配置可使用一个 YAML 文件，密钥放环境变量或现有凭据文件；配置修改后重启即可，首版无需热更新或 Web 管理后台。

## 5. AI 标签

- AI 整理默认同时生成少量标签，通常 2～5 个，内容简单时可更少。
- 标签作为普通 Markdown 中的一行 `#标签` 展示在草稿里，与正文一起确认保存，由 Memos 提取。
- 优先使用可选的常用标签词表，统一技术名称和大小写，减少同义标签；允许必要的新标签。
- 标签与正文在同一次 AI 调用中生成。用户可用自然语言增删标签，单独修改标签时尽量保持正文不变。
- 原样保存不调用 AI，只保留素材已有的标签。未来可增加“原文加 AI 标签”方案。
- 首版无需标签管理系统、复杂分类树或自动合并历史标签。

## 6. 依赖与职责分离

AI 接口优先评估 [OpenAI 官方 Go SDK](https://github.com/openai/openai-go)：它提供两种目标协议、自定义地址和扩展字段能力。采用与项目 Go 版本适配的稳定版本，并在实际中转上验证。只有具体兼容点无法满足时，才在 AI 包内补少量 HTTP 适配。

继续利用 Memogram 已有的 Telegram 库、Memos 客户端、配置和部署基础。不要同时引入功能重叠的多个 AI SDK，也无需 Agent 框架。

职责边界保持简单，具体目录名由开发者结合上游结构决定：

- Telegram 接入：平台认证、指令和按钮解析、文件获取、状态与草稿展示。
- 应用流程：素材组、生成、修改、补充、确认保存；不直接依赖 Telegram SDK 的消息类型。
- AI 调用：供应商／模型配置、协议转换、文字和图片输入、结果与用量读取。
- Memos 调用：读取必要信息、保存正文与附件、返回笔记标识和链接。

平台消息只转换为应用需要的文字、来源、附件引用等少量内部数据；附件通过简单函数或接口获取。会话标识带平台与会话作用域，避免以后接入其他 Bot 时冲突。

未来新增 QQ 或钉钉时，复用应用流程、AI 和 Memos 部分，重写相应平台的收发与交互。首版不写 QQ／钉钉适配，不设计通用事件总线、插件注册表、能力协商或复杂接口继承体系；只有实际使用的边界才需要接口。

## 7. 保存、内存和基本失败处理

- AI 草稿确认之前，不创建 Memos 笔记或上传 Memos 附件。
- 素材主要保存文字和 Telegram 文件标识，图片按需下载，避免把大量附件长期留在内存。
- 不向 AI 发送包含 Bot Token 的 Telegram 文件下载地址；使用下载后的图片数据。
- 同一活动组只运行一次 AI 生成；接收素材与耗时的 AI 请求分开，保留消息顺序。
- AI 失败时保留已有素材和草稿；Memos 保存失败时保留待保存内容。
- 正文已创建但部分附件失败时，记住笔记标识，提示部分成功，重试时补传失败附件。
- 保存或放弃后释放本组数据。重启不承诺恢复草稿、上传进度或跨重启去重。
- 草稿无需持久化，不代表凭据随重启丢失；可沿用原账号绑定文件，也可采用简单的单用户配置。
- 保留必要的单用户访问限制、请求超时和错误提示；日志不输出密钥。无需扩展为复杂权限或审计系统。

## 8. 远期规划

### 其他 Bot 入口

QQ、钉钉等在后续按实际平台能力分别接入，允许使用不同的按钮或命令交互，不追求所有平台界面完全一致。

### 向量与语义搜索

- Memos 始终是正式笔记的主存储，向量索引可从 Memos 重建。
- Embedding 与聊天模型分别配置，不能假设聊天中转也提供 Embedding。
- 未来索引覆盖已有笔记，包括直接在 Memos 中创建的内容，处理更新和删除。
- 按需对长笔记分段，记录 Memos 标识、内容版本和 Embedding 模型／维度；更换向量空间时重建。
- 先做语义检索并返回片段和 Memos 链接，再考虑结合关键词／标签和笔记问答。
- 目前不选定向量数据库，不建立索引，不实现 RAG，也不要求提前创建空的搜索框架。
- 将来的索引持久化与当前草稿只放内存是两件事。文字索引主要利用已保存正文和图注，不默认包含图片像素语义。

## 9. MVP 实施与验收

建议分三步实现：先素材收集和原样保存，再多供应商 AI 草稿与修改，最后图片理解、标签和完整保存闭环。每一步都应可运行，不为远期规划新增运行服务。

核心验收场景：

1. 多条消息间隔几秒发送，文字、链接、图片和相册都进入同一组；选择处理前没有 Memos 写入。
2. 原样保存按接收顺序保留文字和附件，不调用 AI。
3. 简单整理只发送文字与图片说明，不发送图片；教程整理在支持的模型上读取图片。
4. 至少配置两个供应商、多个模型，覆盖两种协议和可选参数的正确发送；可以用模拟服务验证请求。
5. 草稿可以多轮修改、补充资料、增删标签；未纳入的新素材有明确提示。
6. AI 草稿确认后才保存，正文不追加全部原文，标签和附件在 Memos 中可用，链接正确。
7. 同一会话重复确认不会重复创建；AI 失败保留草稿，附件部分失败可以补传。
8. 重启后活动组清空，固定配置仍然有效；Docker Compose 可启动并完成一次收集到保存流程。

只写能验证上述关键行为的测试，不给简单配置访问器或薄封装逐个堆测试。真实 Telegram、AI 中转和 Memos 的联调，应与模拟测试、构建验证区分；缺少凭据时明确报告未验证部分，不伪称通过。

数字映射、默认模型和提示词措辞属于可调整配置，使用本文示例即可，不因这些选择反复中断实施。首次交付记录实际默认值，用户以后可修改。
